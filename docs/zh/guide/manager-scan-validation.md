# 管理器发现与扫描验证

内核根据包列表和构建时指定的包名、证书识别唯一的 ZySU 管理器。`packages.list` 的更新可能由安装、升级或其他包元数据变化引起，不能把每次事件都当作 APK 已变化。本文描述发现范围、扫描缓存和 SuperKey 身份校验的当前行为及验证方法。

## 包名与证书绑定

内核仅识别包名精确匹配 `KSU_MANAGER_PACKAGE` 的管理器，默认包名为 `com.zying.zysu`。签名路径只接受构建时配置的一份证书。包名相似、具有相同前缀或共用该证书的其他应用不能成为管理器。修改包名和证书的构建选项见[编译内核模块](how-to-integrate.md#选项与管理器身份)。

SuperKey 也仅用于该包。签名绕过模式允许该包通过密钥认证，但不会开放其他包名。认证前重新读取包列表；读取或解析失败时拒绝本次认证，不使用旧映射授予身份。管理器卸载或包名与 appid 的对应关系变化时，旧签名身份和 SuperKey 身份都会失效；其他包仍占用相同 appid 不能保留管理器权限。

关闭签名绕过时，密码认证还会重新检查当前 APK 的证书；普通签名认证仍然可用。已发现但尚未认证的目标包保留 prctl 认证入口，这不会提前授予管理器身份、驱动 FD 或 reboot 系统调用权限。认证尝试按 UID 限速，错误密钥不会杀死进程或重启设备。

管理器分别保存修补镜像的输入和成功认证的凭据。生成或刷入使用另一个密钥的镜像只更新下次修补的预填值，必须成功认证后才更新自动登录凭据。旧版本保存的密钥仍可作为升级后的认证候选。

## 发现与调度

主要实现位于 [`kernel/manager/throne_tracker.c`](../../../kernel/manager/throne_tracker.c) 和 [`pkg_observer.c`](../../../kernel/manager/pkg_observer.c)。

- 初始化时安排延迟扫描；包观察器监听 `/data/system` 中 `packages.list` 的创建/移动相关事件。
- 观察回调只调度工作，不在 VFS 事件回调中执行 APK 扫描。扫描使用延迟工作，100 毫秒内的重复通知会合并。
- 包列表中存在目标包且当前尚未识别管理器时，才搜索 `/data/app`。管理器身份仍有效时只更新包列表与授权记录。
- 在打开包目录前先筛选目录名，仅进入目标包目录，以及上层以 `~~` 开头的随机安装容器。兼容 `/data/app/<包名>-<后缀>/base.apk` 和 `/data/app/~~<随机值>/<包名>-<后缀>/base.apk`；其他应用的包目录和 APK 不进入扫描。
- 目录遍历回调只收集 `base.apk` 路径，找到后结束当前目录遍历；元数据检查和签名读取在 `iterate_dir` 返回并关闭目录文件后执行，避免在持有目录锁时再次打开 APK 导致死锁。
- 包列表更新、签名扫描及认证前的包身份刷新共用互斥锁；退出时移除观察，再停止排队、取消工作并释放缓存。
- 读取包列表发生短读、解析失败或分配失败时，放弃本次更新，避免根据不完整列表清理授权记录。

## 缓存命中条件

需要搜索时，扫描仍会枚举上层安装目录，以发现目标包的新安装路径。缓存只记录目标包中已经检查但未获信任的 APK。进入此类目录之前，只有以下信息均未变化才会跳过该目录和签名读取：

| 比较项 | 用途 |
| --- | --- |
| 完整 APK 路径 | 识别安装目录变化 |
| 包对应的 appid | 识别应用身份变化 |
| 设备号与 inode | 识别同路径替换 |
| 文件大小、mtime、ctime | 识别文件或元数据变化 |

元数据获取失败时重新检查；签名读取前后元数据不同的 APK 不进入缓存。缓存只记录不受信任的检查结果，不授予管理器权限。

受信任的管理器 APK 不进入该缓存；需要重新搜索时仍读取其签名。目标包消失或 appid 变化时清空缓存并撤销旧身份。其他包始终在目录筛选阶段被跳过，不依赖缓存命中。

首次发现以及目标 APK 路径、身份或元数据变化后的搜索仍需要真实访问目标 APK。扫描由初始化和包事件调度，不提供用户触发的强制重扫接口，也不维护其他包的候选签名列表。旧的管理器签名配置与列表查询 ioctl 编号 240、241 已停用。该优化不改变系统 inotify 的事件分发语义。

## 主机回归

在仓库根目录执行，需要 Python 3 和本机 Clang：

```sh
python3 scripts/ci/test_manager_scan.py --cc clang
python3 scripts/ci/test_superkey.py --cc clang
```

测试提取生产 C 函数，以模拟 VFS、APK 签名读取和工作队列记录目录打开、签名检查、缓存及授权变化。覆盖打开目录前的包名筛选、目录遍历与 APK 检查的执行顺序、重复扫描、路径/身份/元数据失效、UID 复用、签名检查的包名约束、包列表读取失败以及退出后禁止重新排队。

SuperKey 用例另外覆盖编译密钥与镜像配置优先级、签名绕过开关、按 UID 限速及恢复，以及首次认证前的 tracepoint 标记和权限边界。

自动化入口是 [`.github/workflows/manager-tests.yml`](../../../.github/workflows/manager-tests.yml)。它是内核管理器发现的主机回归工作流，不是 Android 管理器 UI 测试。脚本通过只能证明这些模拟分支符合断言，不能替代完整内核编译、真实文件系统通知或并发验证。

## 设备验证

使用测试设备上的匹配内核和管理器，分别覆盖签名认证、签名与 SuperKey 认证、SuperKey 签名绕过认证场景。记录源码提交、设备 KMI、实际加载的内核模块版本、APK 版本/签名与测试步骤。

1. 触发首次扫描和重复包事件，通过内核跟踪或测试构建中的计数确认其他应用的包目录从未打开、APK 从未读取；管理器已获信任时不重复搜索 APK。
2. 安装、更新、卸载并重装管理器，确认新路径能被发现，身份校验正常；同时覆盖随机安装容器和旧式直接包目录。使用同一证书签名但包名不同的测试 APK，确认其不能获得管理器身份；卸载管理器后保留同 appid 的其他测试包，确认旧签名身份和 SuperKey 身份均被移除。
3. 使用目标包名的未受信测试 APK 覆盖重复扫描、同路径替换、文件内容修改、appid 变化及元数据读取失败，确认缓存仅跳过未变化的检查结果。
4. 在未预先授权的目标包内验证首次 SuperKey 认证，并覆盖管理器早于包扫描启动及模块晚加载。关闭签名绕过时，正确密钥配合不受信任的 APK 证书仍必须失败；开启绕过时允许同一目标包使用该密钥。由其他包使用正确密钥请求认证仍应被拒绝；模拟包列表读取失败，确认不能沿用旧映射认证。
5. 同时触发包事件和 SuperKey 认证，检查死锁、链表损坏、引用泄漏及退出后重新排队等异常。
6. 在隔离的测试设备上验证错误密钥的限速及到期恢复，确认错误输入不触发进程终止或设备重启，其他 UID 的请求不消耗目标 UID 的配额。
7. 使用密钥 A 成功认证，仅生成使用密钥 B 的备用镜像，再启动原内核，确认自动认证仍使用 A。覆盖空白密钥、清除保存数据和“不存储超级密钥”设置。

设备侧目录访问计数需要适当的跟踪或测试构建；仅看到管理器正常启动不足以证明缓存命中。报告中应分开记录功能结果、访问次数和内核日志，不把主机测试输出写成设备实测结果。
